# LCD Rendering — Architecture, Luna Virtual Piano, and Artifact Investigation

## LCD Hardware

- **Panel:** ST7789, 240×320 portrait, SPI1 at ~24 MHz (APB2=96 MHz, divisor 4)
- **Backlight:** PB9, GPIO-high always-on (TIM4_CH4 PWM for dimming is future work)
- **Build gate:** `LUNA_QP_ENABLE = yes` in `rules.mk`; with `no` the firmware is byte-identical to the legacy OLED build
- **Init:** `qp_st7789_make_spi_device(240, 320, ...)` + `qp_init(QP_ROTATION_0)` + full-panel black fill + inversion-off

## Two render paths share one LCD

### 1. OLED-buffer blit (`lcd_blit_oled`)

The legacy OLED renderers (layer/BPM header, transposition, chord name, channel, keylog, every menu, quick build, loop interface, ear trainer, etc.) keep writing into QMK's 2048-byte `oled_buffer` (128×128 px, 16 pages × 128 cols). With no SH1107 on the I²C bus the driver's flush is a no-op, but the buffer is fully populated.

`lcd_blit_oled()` copies the buffer to the ST7789 at 2× scale: each OLED pixel becomes a 2×2 LCD rect. The visible area is 240×256 LCD pixels (OLED cols 0..119 → LCD x=0..239; OLED pages 0..15 → LCD y=0..255). Cols 120..127 clip past the right edge of the 240-wide panel.

To keep SPI traffic low the blit is an **XOR delta**: an in-RAM snapshot (`lcd_prev_oled[2048]`) is compared byte-by-byte against the live `oled_buffer`; only bits that flipped get repainted. Steady-state (no UI changes) emits zero `qp_rect` calls.

Runs from `housekeeping_task_user` every 50 ms (`LCD_BLIT_INTERVAL_MS`).

### 2. Luna QP virtual piano (`luna_qp_render_delta`)

A Quantum Painter native renderer paints a 240×82 px, 3-octave (36-key) piano keyboard directly to the LCD at `(LUNA_LCD_BASE_X=0, LUNA_LCD_BASE_Y=128)` — LCD y=128..209. Sits physically in the same region the OLED-buffer blit maps pages 8..13 onto, but **paints after the blit**, so its pixels take precedence.

Uses `qp_rect` for key fills and `qp_line` for separators/borders. Delta-render variant (`_render_delta`) only repaints cells whose `luna_key_state_t` changed since last frame — idle frames have zero SPI cost.

### Coordination

The OLED-buffer region covering pages 8..15 is **cleared to zero** every frame by an inline `memset` in `oled_task_user` (the legacy `render_luna()` function has been deleted — see §Artifact below). This ensures `lcd_blit_oled`'s XOR delta is zero in that region, so it never overwrites luna's pixels during normal rendering.

When luna is **hidden** (menu/loop/tab active), `housekeeping_task_user` paints a black rect over luna's region (`qp_rect(0, 128, 239, 209, black)`) so the OLED blit has a clean canvas. On the hide→show transition, `luna_qp_invalidate()` forces a full repaint.

Gating condition for luna visibility:
```
hide_luna = any_oled_menu_active()
          || dynamic_macro_has_activity()
          || oledtabmode
```

## How the Luna keyboard decides what keys to light up

### Data flow

```
user press ─────────► trueheldkeyN, held_zones[slot]      ┐
smartchord emit ─────► smartchordkey2..7                   │
cprog tick ──────────► cprog_voices[].step_active_notes    ├─► luna_collect_state()
                                                           │      │
arp note-on ─────────► voice_paint_on(note, ARP, slot)     │      ▼
seq note-on ─────────► voice_paint_on(note, SEQ, slot)     │   luna_key_states[36]
delay echo ──────────► voice_paint_on(note, DELAY, slot)   ┘      │
dynchord ────────────► voice_paint_on(note, DYNCHORD, 0)          ▼
                                                           luna_qp_render_delta()
```

### Data sources (priority order — first writer to a cell wins)

| Priority | Source | Globals read | State enum | When active |
|---|---|---|---|---|
| 1 (highest) | User press | `heldkey1..7`, `trueheldkey1..7`, `octaveheldkey1..4`, `trueoctaveheldkey1..4` | `KEY_BASE`, `KEY_KEYSPLIT`, `KEY_TRIPLE_MID`, `KEY_TRIPLE_RIGHT` | Always |
| 2 | Smartchord | `smartchordkey2..7` | `KEY_SMARTCHORD` | Smartchord mode on |
| 3 | Chord progression | `cprog_voices_snapshot()` | `KEY_CPROG_BASS`, `KEY_CPROG_CHORD`, `KEY_CPROG_LEAD` | Chord prog playing |
| 4 (lowest) | Voice paint | `voice_paint_slots()` (32 slots) | `KEY_ARP`, `KEY_SEQ`, `KEY_DELAY`, `KEY_DYNCHORD` | Arp/seq/delay/dynchord active |

### Held-key system (source 1)

The firmware tracks up to **7 simultaneous user presses** (`heldkey1..7`) plus **4 octave-doubled presses** (`octaveheldkey1..4`). Each slot stores two values:
- `heldkeyN` — note class 1..12 (non-zero = occupied)
- `trueheldkeyN` — absolute MIDI + 24 offset (recover MIDI with `trueheld - 24`)

Zone tagging (`LUNA_ZONE_SET` macro, stamped at all 42 press sites in `orthomidi5x14.c`) classifies each held key into BASE / KEYSPLIT / TRIPLE_MID / TRIPLE_RIGHT based on the keycode range and `keysplittransposestatus`.

### Voice-paint system (source 4)

For notes generated by background engines (arp, seq, delay, dynchord), the firmware can't use `heldkeyN` (those slots are only for physical presses). Instead, `LUNA_BG_ON/OFF` macros fire `voice_paint_on(note, source, idx)` / `voice_paint_off(...)` at the six central MIDI emit wrappers in `process_midi.c`. This populates a 32-slot table (`voice_paint_slot_t`) that `luna_collect_state()` scans every render frame.

### MIDI-to-keyboard-index mapping

`midi_to_kbd(midi)` maps any MIDI note to a keyboard cell index 0..35 by subtracting `luna_display_first_midi` and wrapping modulo `LUNA_NUM_KEYS` (36). Notes above the displayed window fold down; notes below fold up.

`luna_display_first_midi` defaults to 24 (C0 in firmware display convention) and is updated by the OLED keyboard mode selector (`oledkeyboard_shift`): mode 1 → C0, mode 2 → C1, mode 3 → C2.

## Top-right LCD artifact — investigation and resolution

### Symptom

A sparsely-populated block of black and white pixels appeared near the top-right of the LCD (approximately OLED cols 80..119, pages 0..5 = LCD x≈160..239, y≈0..95). The pattern resembled the legacy OLED piano-keyboard sprite. Pixels alternated at roughly 50% between the correct text content (BPM, transposition) and the keyboard render, frame to frame. Present at boot — no arp/seq/delay needed to trigger it.

### Bisection results

| Step | Change | Artifact? |
|---|---|---|
| 0 (baseline) | Legacy `render_luna` neutralized (memset + return), luna_qp wired | **YES** |
| 1 | Deleted legacy `render_luna` (918 lines), added `oledtabmode` hide gate | YES (user reported) |
| 2 | Gated off ALL 4 inherited data sources (smartchord, cprog, voice_paint reader, voice_paint writer) | **NO** |
| 3 | Re-enabled smartchord + cprog (voice_paint still off) | NO |
| 4 | Re-enabled voice_paint writer (`LUNA_BG_ON/OFF` hooks in process_midi.c), reader still off | NO |
| 5 | Re-enabled voice_paint reader (section 4 of `luna_collect_state`) — everything on | NO |

### Conclusion

### Updated diagnosis (2026-05-24)

**Stale GRAM from previous firmware flash.** The artifact is the old
`render_luna` piano keyboard image, still sitting in the ST7789's GRAM from
a prior firmware build. The ST7789 retains GRAM contents across power cycles
and resets — it only loses content if the panel is physically powered off
(VDD removed) or if software explicitly overwrites it.

During `keyboard_post_init_user`, `qp_rect(0, 0, 239, 319, 0, 0, 0, true)`
is supposed to overwrite the full panel with black. But the ST7789 datasheet
requires **120 ms minimum** after SLPOUT (sleep-out) before GRAM writes are
reliable. QMK's `qp_init` sends SLPOUT but does not always wait long enough.
If the full-panel black rect arrives before GRAM is ready, the write silently
fails and the old image persists.

This matches all observations:
- **Intermittent:** depends on exact boot timing — sometimes the MCU reaches
  the black-fill fast enough to race the 120ms window, sometimes not
- **Recognizable image:** it's the exact old piano keyboard, not random noise
- **Top-right location:** the old render_luna wrote to different LCD coordinates
  than the current code
- **Present at boot only:** once the first `lcd_blit_oled` cycle overwrites
  GRAM with actual UI content, the stale region is painted over (if it
  overlaps with the blit's page range)

### Fix applied

```c
// In keyboard_post_init_user, after qp_init + qp_power:
wait_ms(150);                    // guaranteed > 120ms SLPOUT settling
qp_clear(luna_lcd);
lcd_disable_inversion(luna_lcd);
qp_rect(..., 0, 0, 0, true);    // first full-panel black
qp_flush(luna_lcd);
qp_rect(..., 0, 0, 0, true);    // belt-and-suspenders second pass
qp_flush(luna_lcd);
```

### Debug gates — removed

The bisection compile-time gates have been removed:
- `luna_state.c`: `LUNA_STATE_SRC_SMARTCHORD/CPROG/VOICE_PAINT` defines + `#if` blocks
- `process_midi.c`: `LUNA_QP_DISABLE_INHERITED_SOURCES` define + `#if` block

All data sources now compile unconditionally.
